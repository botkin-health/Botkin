# ADR-0012: Состояние пользователя (превью еды) — JSON-файлы в `/app/data/state`, а не таблица Postgres

**Дата:** 2026-10-31 · **Статус:** Accepted · **Автор:** Александр Лысковский (с Claude)

## Контекст

`services/state.py` `StateManager` держал состояния пользователей (превью еды перед «Сохранить», ожидание подписи к фото, подтверждение веса/БАДов) в dict процесса. Каждый деплой перезапускает контейнер бота, а при выкатке багфиксов деплоев бывает несколько за вечер. Открытые в этот момент превью терялись: «Сохранить» отвечал «⚠️ Состояние истекло. Отправьте фото заново.», запись не попадала в `nutrition_log`.

Прецедент 30.10.2026: превью собрано в 20:59:20 UTC, рестарт от деплоя в 20:59:29, суп пользователя не сохранился.

Ограничения:
- Интерфейс `get_state` / `set_state` / `clear_state` синхронный, вызывается из ~30 мест в хендлерах. Менять хендлеры не хотим.
- Бот — один процесс на один контейнер (webhook), горизонтального масштабирования нет.
- `/app/data` на проде и деве — bind-mount хоста (`/opt/botkin/data`, `/opt/botkin-dev/data`), там же лежат фото из превью (`data/media/nutrition/…`), на которые ссылается `photo_paths`.

## Решение

Память остаётся основным кэшем (хендлеры получают тот же объект, что и раньше). `set_state` дополнительно атомарно пишет `data/state/<user_id>.json` (tmp + `os.replace`), `clear_state` его удаляет. `get_state` при промахе в памяти читает файл — так состояние переживает рестарт.

- **TTL 24 ч** (`DEFAULT_TTL_SECONDS`): старое состояние не восстанавливается ни из памяти, ни с диска; при старте процесса просроченные и битые файлы удаляются.
- **Типы:** `data` кодируется в JSON с метками для `Path`, `date`, `datetime`, `time` и декодируется обратно в те же типы. Tuple/set становятся list, Decimal — float, Pydantic-модель — dict.
- **Сбой диска не роняет хендлер.** Если `data` не сериализуется (неизвестный тип) — состояние живёт только в памяти, а старый файл удаляется, чтобы после рестарта не восстановилась устаревшая копия.
- `BOT_STATE_DIR` переопределяет каталог; пустая строка выключает персистентность (так делает `tests/conftest.py`).

## Почему не таблица в Postgres

- Интерфейс синхронный, а запись в БД из async-хендлера — это блокирующий сетевой вызов на каждый `set_state`, плюс риск держать транзакцию поперёк LLM-вызова (см. анти-паттерн про `idle_in_transaction_session_timeout` в CLAUDE.md).
- Нужна миграция и отдельный прогон «Migrate DB» на деве и проде — больше движущихся частей ради эфемерных данных с TTL в сутки.
- Превью без фото бесполезно, а фото и так лежат в `/app/data`: файловое состояние живёт и умирает вместе с ними (бэкап/перенос `/opt/botkin/data` переносит оба).
- Одна запись на пользователя, один процесс — конкурентного доступа нет, транзакции не нужны.

Postgres станет нужен, если бот разделится на несколько реплик или процессов: тогда состояние надо делить между ними, и файлы на одном хосте не подойдут. Интерфейс `StateManager` позволяет заменить бэкенд без правки хендлеров.

## Последствия

- На диск попадает только то, что прошло через `set_state()`. Правка `user_state.data[...]` на месте без повторного `set_state()` после рестарта потеряется. Сейчас все хендлеры после правки вызывают `set_state()`. Новые места должны делать так же.
- `user_id` и `int`, и `str` указывают на один файл (`str(user_id)`). Ключи не вида `[A-Za-z0-9_-]+` на диск не пишутся.
- Состояния aiogram FSM (`MemoryStorage` в `telegram-bot/bot.py`: загрузка документов, настройка профиля, подключение CGM) это решение не покрывает — они по-прежнему теряются при рестарте.
